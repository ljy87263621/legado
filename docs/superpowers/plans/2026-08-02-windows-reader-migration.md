# Windows Reader Migration Implementation Plan

**Goal:** Migrate the Android Legado reader to a Windows desktop application while preserving the Android reader's user-facing capabilities and data model.

**Architecture:** Keep Android-compatible concepts in `modules:core`, use `desktop:core-persistence` for durable local state, and keep Compose Desktop UI and Windows-specific integration in `desktop:app`. Each migrated capability must have a model/service boundary, a user-visible route or control, and tests against both in-memory and SQLite-backed storage where persistence is involved.

**Tech Stack:** Kotlin/JVM 17, Compose Desktop Material 3, SQLite JDBC, Gson, Jsoup, JSONPath, Java standard library ZIP/HTTP/TTS integrations where suitable.

## Global Constraints

- Preserve Android-compatible book, chapter, source, bookmark, group, progress, and reader-setting semantics.
- Desktop distribution must remain a portable or directory-installable Windows build and must not require MSIX/AppX registration.
- Use the existing `CoreLibrary` boundary instead of coupling UI code to SQLite.
- Every user-visible feature must be reachable from the desktop GUI and have focused automated tests.
- Keep Android source and existing user changes intact; do not remove Android functionality as a migration shortcut.

## Migration Workstreams

1. Reader foundation: bookshelf, local import, source search, details/catalog, reader content, progress, bookmarks, settings, and RSS subscriptions.
2. Data portability: local backup/restore, Android JSON compatibility, optional WebDAV sync, and source/book migration safety.
3. Reader behavior: real paged layout, scroll/paged controls, auto-read, replacement rules, text cleanup, dictionary and TXT TOC rules.
4. Source engine: JavaScript/Rhino execution, cookies/login/source variables, source debug, source filters, and source auto-update.
5. Offline and media: chapter download/cache, update tasks, audio/video/image/comic readers, and media-specific controls.
6. Desktop integrations: file associations, keyboard shortcuts, local server/config management, logs, release packaging, and runtime verification.

## Current Increment

The current independently testable increment combines book-source script execution, desktop source management, and reader navigation. The JVM core runs source `@js:` and `<js>` rules through a restricted Rhino runtime with a timeout, Java class access disabled, shared `jsLib`, and contextual errors. Search, dynamic headers and URLs, book-info initialization, `preUpdateJs`, TOC formatting, content-title scripts, and the explicit browser-dependent `webJs` boundary are covered by focused tests. The desktop source route can import/export sources, edit a complete source JSON document, and run a rule script against supplied input with `source`, `baseUrl`, `result`, `input`, and `src` bindings. Local ZIP backup/restore remains available from settings and is covered separately.

The reader slice now has real scroll and fixed-capacity paged presentation paths, chapter navigation, position restoration, keyboard commands, page counters, automatic page/chapter advancement, and a persisted 1-120 second automatic-reading interval. The SQLite adapter migrates older `desktop_settings` tables by adding the new interval column, and old JSON backups without that property retain the default interval. Bookmarks now have a searchable desktop panel with excerpts, deletion, and direct chapter/position restore; reading records have per-book aggregation, duration/session counts, search, sorting, open-book navigation, deletion, and a UTF-8 Markdown export action that writes a summary, per-book totals, and stable session details using raw day keys and epoch seconds. Reading records now also have a tested monthly heatmap Windows subset: it filters by `yyyyMMdd` month, clamps negative durations, uses a Monday-first calendar with leap-year lengths, applies the Android-compatible six-level/12-hour scale, supports previous/next month navigation up to the current month, shows monthly totals, and allows day-duration inspection. The grid height is derived from its row count so 31-day months are not clipped. Markdown import/sync and full Android statistics remain future work. The heatmap behavior is covered by `ReadRecordHeatmapModelTest`; it does not claim Android `ReadRecordActivity` parity. Replacement rules now have a shared model/service, title/content scope filtering, book/source include and exclude scopes, timeout protection, SQLite persistence, backup/restore, single-rule testing, and a desktop management route. TXT import now uses the Android-compatible rule model and full default rule resource, filters enabled rules, selects the rule with the strongest spaced match count, merges leading text into the first chapter, falls back to a single正文 chapter when no rule matches, and persists/backs up custom rules; the desktop now also provides a TXT-rule editor, enable toggle, delete action, JSON import/export, and settings entry. Local chapters preserve original byte ranges and missing cached content can be read lazily by range; very large-file performance and all Android chapter-splitting details remain future work. Windows reader pages also expose system read-aloud controls backed by PowerShell `System.Speech.Synthesis.SpeechSynthesizer`; HTTP TTS, multi-engine configuration, and complete Android read-aloud semantics remain future work. Book details now search same-title and same-author candidates, retain the current source, switch only after loading the replacement details and chapters, preserve bookshelf groups, and roll back an uncommitted replacement on failure; the flow is wired into the desktop detail screen and covered by model tests. These behaviors are covered by core, persistence, model and backup tests and the desktop source compiles into a Windows EXE.

Book discovery is now a tested desktop subset: it filters and selects eligible sources, expands `exploreUrl` with static category options and page numbers, parses `ruleExplore`, refreshes and appends deduplicated pages, applies enabled source-discovery filter rules before pagination, and exposes add-to-bookshelf and detail navigation actions. The Windows filter subset supports `NAME`, `AUTHOR`, `INTRO`, `KIND`, and `WORD_COUNT`, with all-source, one-source (`source::URL`), and source-group scopes. Rules have SQLite CRUD, ZIP backup/restore, and a Settings management route with enable toggles, add/edit/delete, and JSON import/export; the Explore page reports filtered results and invalid enabled rules. Source variables and source-aware persistent/session Cookies are now resolved by discovery and the shared online service. Android's source ranking, auto-update, login UI/WebView session state, full script semantics, WebView-dependent behavior, dynamic filter scripts, and complete dynamic explore-option JavaScript remain future work.

Bookshelf updates now have a tested desktop task subset: the bookshelf queues eligible online books, refreshes each table of contents through the existing online service, persists the check timestamp and newly added chapter count, continues after individual failures, retries transient failures, publishes per-book progress, and exposes pause/resume/cancel controls while retaining completed results. The desktop app also persists a 15-minute-to-24-hour background update schedule, restores it when the database is reopened, runs due work on a daemon scheduler thread, exposes enable/interval/status controls in Settings, refreshes the bookshelf after completion, and stores the schedule in local ZIP backups. The book detail page now provides an in-process chapter download queue with cache skipping, per-chapter success/failure results, progress, pause/resume and cancel controls. Download tasks persist in SQLite, interrupted `IDLE/RUNNING` tasks recover as `PAUSED`, unfinished tasks can be resumed when the book is reopened, and task records are included in local ZIP backup/restore. Background notification semantics and Android-compatible download-record parity remain future work.

Dictionary lookup now has a tested Windows subset. Desktop rule management and reader lookup support `{{key}}` URL expansion, the shared URL-option subset (`method`, `body`, `charset`, `headers`), raw responses, CSS/JSONPath/basic-regex extraction, enabled-rule ordering, per-rule error retention, and newline-joined text from all CSS matches. Full Android `AnalyzeRule` composition, complex dynamic URLs, embedded JavaScript, browser-dependent URL options, complete XPath/JSON/JS `init`, and WebView/browser-dependent behavior remain future work.

Source debugging now has a tested Windows request-inspection subset. The source editor can execute one asynchronous resolved HTTP request, using GET by default and supporting the shared URL-option method/body/charset/headers subset, resolve the current source's dynamic `header` rule and source variables, reuse source-aware persistent/session Cookies when enabled, accept manual headers as JSON or `name: value` lines with manual override precedence, and display request metadata, the final URL, status code, response headers, response body, and transport/non-2xx errors. The local management bridge also exposes a constrained `/bookSourceDebug` WebSocket request log. This increment intentionally does not claim Android `BookSourceDebugActivity` parity: the complete source validation pipeline, per-rule trace, login UI, WebView/WebView2 verification, browser-session sharing, and full dynamic script debugger remain future work.

The source editor also has a tested browser-verification launch subset. The desktop model validates an HTTP(S) URL and opens it through an injectable system-browser launcher, carrying the current source URL and name as request metadata. This does not embed WebView2, capture page results, share Android WebView cookies, run CAPTCHA callbacks, or wait for Android `getVerificationResult`/`refetchAfterSuccess`.

Local image/comic reading now has a tested Windows subset. The desktop file importer accepts standalone images plus `.cbz`/`.zip` archives, filters supported bitmap entries, natural-sorts pages, groups archive directories into chapters, keeps root images under `正文`, persists image chapters without fabricated text content, and preserves progress on re-import. The reader route now uses a local-image-book predicate so only `loc_book` image books enter the filesystem-backed image reader; online image books continue through the existing reader path. The GUI displays image pages with chapter/file labels, global page counts, previous/next page and chapter controls, 50%-300% zoom, reset zoom, save position, and keyboard navigation with left/right, space, Ctrl+left/right and `S`.

The local management bridge now has a tested Windows subset with three constrained write paths and two WebSocket routes. Settings starts and stops loopback-only services, validates the configured HTTP port, shows and copies both endpoints, and lists the supported routes. The HTTP service uses port `N`; the WebSocket service uses `N + 1`; both bind only to `127.0.0.1`. The bridge uses the Android-compatible `isSuccess`/`errorMsg`/`data` JSON envelope for HTTP responses. `/health`, `/getBookshelf`, `/getBookSources`, `/getGroups`, `/getChapterList?bookUrl=...` (also accepting Android's `url` parameter), `/getBookContent?url=...&index=...`, and `/getReadConfig` expose the current `CoreLibrary` state through real loopback requests. `/searchBook` accepts `{"key":"..."}` and returns a flat Android/Web-compatible `SeachBook[]`; `/bookSourceDebug` accepts `{"tag":"sourceUrl","key":"..."}`, emits the desktop request URL/status/headers/body/error log subset, and closes the connection. `/getBookContent` reads cached desktop chapter content only and returns an error when the chapter or content is absent; it does not invoke the Android online fetch pipeline. `POST /saveBook` accepts a full Android-compatible `CoreBook` JSON object, rejects a blank `bookUrl`, and inserts or replaces the desktop book through `CoreLibrary.saveBook`; it intentionally does not perform Android `AppWebDav.uploadBookProgress`. `POST /saveBookProgress` accepts Android `BookProgress` JSON (`name`, `author`, `durChapterIndex`, `durChapterPos`, `durChapterTime`, and optional `durChapterTitle`), matches an existing desktop book by `name + author`, and persists the reading-progress fields through `CoreLibrary.saveBook`. `POST /saveReadConfig` accepts the `modules:web` `webReadConfig` schema, rejects missing or out-of-range fields, stores the validated value as normalized JSON, and persists it in SQLite through the separate `desktop_web_read_config` table. The value survives a database reopen and a management-server restart; the endpoint itself is available only while the local service is running. Settings is the GUI boundary for service lifecycle, port, both endpoints and route disclosure. The WebSocket debug route is only a desktop request-log subset, not the full Android WebView/XPath/JS/CAPTCHA debugger. Other POST/write/import APIs, static web assets, authentication, LAN exposure, image/cover endpoints, full Android `Book.ReadConfig`/`ReadBookConfig` parity, replacement-rule APIs, WebDAV synchronization side effects, online fetching, WebView/WebView2, and Android service/notification parity remain future work.

The desktop shell now also has a verified first-run setup subset. Startup route resolution sends a new unmarked SQLite data directory to a native `欢迎` screen, persists completion in `desktop_setup`, and then navigates to the bookshelf. Reopening the database retains the marker; a legacy database containing books is treated as initialized even without the new marker, and an external subscription-import launch still opens subscriptions directly. The GUI and state behavior are covered by `AppRouteTest`, while SQLite restart and legacy-database behavior are covered by focused persistence tests. This does not migrate Android welcome preferences, permission prompts, default source onboarding, or Android service setup.

Local audio reading now has a tested Windows subset. The desktop importer recognizes one local `.wav`, `.aif`, `.aiff`, `.au`, or `.snd` file as an Android-compatible local audio book with one playable chapter. The audio reader GUI exposes play/pause, stop, chapter selection, previous/next chapter controls, save-position, and keyboard navigation. `AudioReaderModel` uses an injectable playback-session boundary for tests and the JDK `javax.sound.sampled` Java Sound backend in production; changing chapters and closing the reader release the current session and progress is saved through `CoreLibrary`. The implementation deliberately does not claim MP3/M4A support, Android Media3/ExoPlayer parity, remote audio, background playback, media notifications, audio focus, media buttons, wake locks, sleep timers, network cookies, or audio caching.

The script increment intentionally does not claim Android parity. It provides a safe, testable JVM subset and an explicit failure for browser-dependent rules. Source variables now have CoreLibrary/SQLite persistence and `source.getVariable()`/`source.setVariable()` bindings; source-aware HTTP also persists eligible Cookies and keeps session Cookies in memory. Full Android `JsExtensions`, login UI/WebView cookie state, browser-dependent/full URL-option semantics and embedded rule fragments, XPath/JSON/JS `init` semantics, `refreshTocUrl()`, `coverDecodeJs`, review scripts, and WebView execution remain separate workstreams.

WebDAV remote backup now has a tested Windows subset. Settings persists an HTTP(S) endpoint and Basic Authentication credentials in SQLite, performs a `PROPFIND` connection/list operation, shows safe single-level `backup*.zip` remote files, uploads local ZIP backups with `PUT`, downloads selected backups with `GET`, and restores them through the existing ZIP import path. The settings GUI exposes configuration, refresh, remote selection, upload and restore actions, with network work dispatched off the UI thread. The Java `HttpClient` transport uses bounded timeouts and disabled redirects; DAV XML parsing disables external entities and DTDs. This increment is intentionally remote backup/restore only: no two-way reading-progress synchronization, background sync, remote book library, conflict resolution, image synchronization, Android service/notification parity, or encrypted Android preference semantics are claimed.

The Android difference for this workstream is explicit: Windows does not implement Android's full WebDAV sync contract, progress or image synchronization, automatic/background scheduling, remote library behavior, conflict resolution, or Android service and notification lifecycle. The WebDAV credentials are local desktop SQLite configuration rather than Android encrypted preferences.

## RSS Article Reading Subset

The Windows subscription route refreshes enabled RSS sources through the shared source parser, opens an article as an RSS `CoreBook` with one `CoreChapter`, and routes it into the ordinary desktop reader. When the source has a `ruleContent`, the reader fetches and parses the article body through `OnlineBookService`, resolves relative article URLs against the response URL, and caches the resulting content in `CoreLibrary`; a second open is served from that cache. When no content rule exists, the article summary is stored as the chapter's initial cached content. RSS source, article, chapter and content records survive closing and reopening the desktop SQLite database.

This is a tested Windows RSS article subset, not Android parity. Android's summary-first `ReadRssActivity` presentation, `AnalyzeUrl`/WebView fallback, `clHtml()` CSS injection, WebView JavaScript and `webJs`, shared WebView Cookie/session state, and the complete RSS refresh/cache/read lifecycle remain outside the Windows boundary.

## Windows URL Protocol Association Subset

Windows URL protocol association now has a tested desktop subset. Startup attempts to register `yuedu://` and `legado://`, and the Settings page exposes a visible `注册协议关联` action that can retry registration and shows either the registered state or the preserved `reg.exe` error. Registration writes per-user `HKCU\Software\Classes` protocol handlers, generates UTF-16LE/BOM `.reg` content, imports it with System32 `reg.exe`, and serializes concurrent attempts with a lock. The registration result is modeled separately from the GUI so success, unsupported-platform, missing-executable and command-failure states are testable.

This association is optional Portable integration: the directory build still starts without registry entries, and registration failure does not block the application. Android owns these schemes through intent filters and activity routing; the Windows subset instead resolves the current `Legado.exe` and writes the current user registry. It does not provide Android back-stack/lifecycle behavior or administrator-wide registration. Supported local file-extension associations are covered separately by the Windows file-extension subset below.

## Windows File-Extension Association Subset

Windows file-extension association now has a tested desktop subset. Startup and Settings can register the current user association for `.txt`, `.epub`, `.bmp`, `.gif`, `.jpeg`, `.jpg`, `.png`, `.webp`, `.cbz`, `.zip`, `.wav`, `.aif`, `.aiff`, `.au` and `.snd`, which are the formats currently accepted by the local importer. The generated UTF-16LE/BOM registry file writes each extension, a Legado ProgID, and a `shell\open\command` handler using the current `Legado.exe` and `%1`; System32 `reg.exe import` and a registration lock keep the operation per-user and serialized. Settings retains the registered, unsupported, missing-executable or command-failure state so registration can be retried without blocking Portable startup.

An associated absolute Windows path becomes a typed `DesktopLaunchRequest.localFilePath`. Option values, URLs, relative paths and unsupported extensions are excluded. Startup reuses `LocalBookImporter`, persists the normal desktop records, and opens the imported book in the text, image/CBZ or local-audio reader. Import failures remain visible in the existing desktop error surface and do not terminate the process. Focused tests cover path classification, extension coverage, registry command content, model retry state, startup routing and import success/failure. This is not Android parity: Android uses document/file Intents, URI permissions, Provider streams and Activity lifecycle/back-stack behavior; Windows uses filesystem paths and current-user registry classes and does not implement SAF, provider permissions, share/result callbacks, background import or network-file handling.

## Verification Gates

- Run the focused core and desktop tests after each model/service change.
- Run all `modules:core`, `desktop:core-persistence`, and `desktop:app` tests after cross-module changes.
- Build the portable Windows EXE with `:desktop:app:packageExe` before reporting a deliverable.
- Keep a written list of Android capabilities that remain unimplemented; do not claim full parity until each item has GUI and behavioral evidence.

## Current Android Gaps

- Android `JsExtensions` and complete book/chapter variable persistence; desktop source-variable persistence is limited to the source URL boundary.
- Login UI and `loginCheckJs`, login headers, WebView/browser cookie sharing, and Android cookie-switch semantics; desktop source-aware persistent/session Cookies and `enabledCookieJar` behavior are implemented.
- Complex dynamic URL fragments, `{{...}}` embedded JavaScript, browser-dependent URL options, and full Android URL-option semantics.
- Full XPath/JSON/JS `init` rule semantics and complete `refreshTocUrl()` behavior.
- Browser/WebView `webJs`, `coverDecodeJs`, and review/paragraph-comment scripts.
- Full Android source debugging: complete source validation, per-rule execution trace, login UI, WebView/WebView2 verification, embedded browser state, verification result callbacks, and dynamic script debugging. The desktop request-check subset supports the shared URL-option method/body/charset/headers subset, source variables and source-aware persistent/session Cookies, and displays request/response inspection; `/bookSourceDebug` provides only the desktop request-log subset, and the browser slice only launches a validated URL in the system browser.
- Android `HttpServer`/`WebSocketServer` parity: the desktop bridge is loopback-only for the documented HTTP routes, constrained `POST /saveBook`, `POST /saveBookProgress`, `POST /saveReadConfig`, and WebSocket `/searchBook` and `/bookSourceDebug` routes. HTTP binds to port `N`, WebSocket binds to `N + 1`, and `/searchBook` returns a flat Android/Web-compatible `SeachBook[]`. `/bookSourceDebug` emits the desktop request URL/method/headers/body/status/response/error subset and then closes; it is not the full Android WebView/XPath/JS/CAPTCHA debugging state machine. `POST /saveBook` accepts a full Android-compatible `CoreBook` JSON object with a non-blank `bookUrl`, but does not perform Android WebDAV progress upload. `POST /saveReadConfig` supports only the `modules:web` `webReadConfig` schema, not full Android `Book.ReadConfig`/`ReadBookConfig` semantics. Other write/import APIs, static web assets, authentication, LAN exposure, image/cover APIs, replacement-rule APIs, WebDAV synchronization side effects, online content fetching, WebView/WebView2, and Android service/notification behavior are not implemented. WebDAV itself is limited to the documented desktop remote ZIP backup/restore subset and does not synchronize progress or images, run in the background, expose a remote library, or resolve conflicts.
- Source auto-update, Android's complete source-filter/script semantics, concurrent-rate semantics, and complete explore/review flows. The Windows result-filter subset is limited to the documented fields and scopes above and does not implement Android's dynamic scripts or cache behavior.
- Audio, video, network image/comic sources, long-strip/double-page image modes, touch gestures, filters, prefetch/cache behavior, full Android auto-read semantics, complete Android replacement-rule semantics, the full Android dictionary `AnalyzeRule` semantics, and complete Android TXT TOC behavior including byte-level chapter offsets. The desktop local image/CBZ reader, local audio reader, dictionary lookup, and TXT-rule editor/JSON management paths are implemented as tested Windows subsets. Audio remains limited to Java Sound-compatible local WAV/AIFF/AU/SND files; Android Media3/ExoPlayer, remote URLs, background playback, audio focus, media buttons, notifications, wake locks, sleep timers, and network audio caching are not implemented.
- Persistent Android-compatible chapter download records and background update notifications. Desktop chapter download work, SQLite persistence, restart recovery, ZIP backup/restore, scheduled book updates, retry/progress/pause semantics, and schedule backup/restore are implemented as tested Windows subsets.
- Complete desktop-wide keyboard shortcut configuration, full local server/config management beyond the documented GET routes and constrained progress/read-config POSTs, and clean-profile portable upgrade/signing verification. URL and file associations remain limited to the tested per-user subsets described above; network files and unsupported local formats are not claimed.
- Android welcome onboarding preferences, permission prompts, default source initialization and service setup. Windows has only the native startup acknowledgement and SQLite completion marker described above.
